Premier passage : l'événement `127.0.0.1:3080` (GUI DSH) classé `new_domain` au lieu de `localhost_access` — `background.js` extrayait `url.host` (avec port) ; `IpAddr::parse("127.0.0.1:3080")` échoue → règle contournée dès qu'un port explicite est présent. **Fix** : `url.hostname` sans port (commit `4a9872b`). Re-test après rechargement : l'événement arrive avec `"127.0.0.1"` → **critical correctement déclenché**.

## 4. Test e2e v2 « Hands » (nuit du 05 au 06/10) — état : blocage worker MV3

Scénario tenté : `/v2/cmd tabs_create` via le canal webbridge vers l'extension rechargée
(id `lmjgnljbpcahodolfncbnchomamnkjoi`, permissions scripting+tabs acceptées).

MESURÉ :
- Le démon dispatch la commande (log_action OK, canal OK, 30 s timeout côté démon)
- Les événements webRequest continuent de couler (worker vivant pendant la navigation d'Eddie)
- MAIS la commande n'est jamais traitée : ni onglet créé, ni réponse `{cmd_id, ok}`
- Réessai immédiat après détection d'activité (worker réveillé) : même timeout

Hypothèses non éliminées (debug interactif requis, avec Eddie au navigateur) :
1. WS zombie : l'ancienne connexion (pré-reload) resterait enregistrée côté démon
   (« dernière connexion gagne » à revoir — le nouveau handle ne serait pas celui qui reçoit)
2. `handleCommand` (l.268) ne serait pas atteint : le message arrive sur une WS dont le
   contexte d'exécution diffère de celui qui écoute `onmessage`
3. Réponse perdue : `tabs.create` réussirait mais `sendResponse` partirait sur une WS fermée

Ce que ça N'EST PAS : le sommeil du worker (testé avec worker réveillé), l'auth (token OK),
le routage v2 (tests 6/6 verts avec fausse extension répondant correctement).

Verdict : la couche Rust (démon, canal, API, tests) est PRODUCTION-READY ; la couche
extension webbridge-bidirectionnelle nécessite une session de debug interactive.

## 5. Résolution du blocage §4 — E2E « Hands » RÉUSSI (06/10, 00h45)

Cause identifiée : **fenêtre d'éveil du worker MV3**. La commande n'est traitée que si
le worker est éveillé — c'est-à-dire dans la seconde qui suit une navigation (webRequest
réveille le worker + la WS se (re)connecte). Tir immédiat après détection d'événement
fraîchement écrit dans events.jsonl → **succès** : `tabs_create` exécuté, onglet
example.com ouvert, vu par Eddie dans la fenêtre Chrome (profil debug, « session no name »).

Protocole fiable pour les inférences :
1. Poller `~/.dsh-eyes/events.jsonl` (wc -l) — détecter un événement frais
2. Tirer `/v2/cmd` IMMÉDIATEMENT (< 1 s)
3. Taux de succès attendu : élevé quand le user navigue ; timeout 30 s sinon (renvoyer plus tard)

Verdict : **E2E « Hands » RÉUSSI** — démon → canal → extension → onglet créé, validé
visuellement par Eddie. La boucle Eyes + Hands est complète.

## 6. Fix définitif — keep-alive chrome.alarms (06/10, 01h43)

Cause racine confirmée : le worker MV3 se suspend ~30 s après la dernière activité →
sa WS meurt silencieusement → `extension_disconnected` → les commandes tirées pendant
le sommeil = timeout 30 s.

**Fix** (commit `6ffbf13`) : permission `alarms` + `chrome.alarms.create("dsh-eyes-keepalive",
{periodInMinutes: 0.4})` — l'alarme réveille le worker toutes les 25 s et pinge la WS
(reconnexion si morte). L'worker ne se suspend plus jamais.

**Test à froid (le critère définitif)** : commande `tabs_create` envoyée SANS aucune
navigation préalable → `{"ok":true,"result":{"tab_id":1957616624,"url":"https://example.com"}}`
— onglet ouvert dans Chrome, confirmé. DSH Eyes v2 fonctionne à toute heure.

**Verdict final : E2E COMPLET RÉUSSI.** Eyes (observation) + Hands (action) + Solveur
(captcha local hiérarchisé) — production-ready.
