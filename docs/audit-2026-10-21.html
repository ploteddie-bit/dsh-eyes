Résumé exécutif

DSH Eyes est déjà un outil avancé : démon Rust léger, extension MV3 à 19 commandes, huit gestes natifs via chrome.debugger, vigie de navigation, solveur de captcha en cascade, enregistrement d'écran et serveur MCP. Le socle fonctionne : /health répond, le canal se rétablit, tabs_create et read mode:outline répondent en moins d'une seconde.

Mais le niveau de fiabilité n'est pas encore celui d'un pilotage M2M autonome. Cinq problèmes dominent :

  1. Canal WebSocket sans authentification et « dernière connexion gagne » : un test ou une page web peut remplacer l'extension et tuer le canal. Prouvé pendant l'audit.
  2. Fuite de sockets : deadlock à la fermeture WS, 15 sockets CLOSE-WAIT accumulés en 8 h ; disparus au redémarrage.
  3. SSRF via /v2/cmd : le garde-fou d'hôte n'est appliqué qu'à /v2/open et /v2/goto.
  4. Humanisation inversée : les gestes natifs (isTrusted=true) ont les trajectoires les moins humaines ; la belle humanisation est branchée sur les gestes JS détectables.
  5. Déploiement fragmenté : trois copies de l'extension, noms de dossiers trompeurs, aucun handshake de version, MCP absent de VS Code.

2. Architecture actuelle

Chrome (extension MV3) ↔ WebSocket ws://127.0.0.1:8445/ws ↔ démon Rust (axum + tokio) → routes HTTP v1/v2 et serveur MCP stdio. L'extension sert à la fois de vigie (événements de navigation) et de mains (exécution des commandes via chrome.tabs, chrome.scripting et chrome.debugger).

  • Routes v1 ouvertes : /health, /stats, /events, /ws.
  • Routes v2 avec Bearer : /v2/ping, /v2/cmd, /v2/open, /v2/read, /v2/goto, /v2/click, /v2/fill, /v2/wait, /v2/record/*, /v2/page/*.
  • Concurrence : globale, pas par onglet côté démon ; un seul sink « dernière connexion gagne » ; sérialisation par onglet côté extension seulement.
  • Timeouts : extension 30 s, geste natif 15-24 s, commande globale 25 s, Ollama 60 s/tier.

5. M2M ou navigation humaine : deux modes, un même moteur

ExigenceM2M déterministeNavigation humaine
ObjectifExécuter une séquence reproductible, vérifiable, idempotenteSe comporter comme un opérateur : trajectoires, pauses, lecture, hésitation
Primitivesgoto, read, find, click_native, type_native, wait_forMêmes primitives + profil de mouvement, pauses, scroll, focus
Preuveverified, code HTTP, capture, diff DOM stableVidéo, trace d'actions, signaux d'activité
Faiblesse actuellePas de batch, pas d'idempotence, pas d'annulation, cibles mono-frameHumanisation branchée sur le mauvais chemin (JS détectable)
Constat central. Le mode qui se veut humain (gestes CDP isTrusted=true) est aujourd'hui le moins humain : trajectoire linéaire 3-8 points, bruit ±1 px, frappe sans typos. Le mode qui est le plus humain (Bézier, typos, délais lognormaux) produit des événements isTrusted=false, immédiatement identifiables. Il faut inverser ce branchement.

6. Plan d'amélioration

Phase 0 — Quick wins (1 à 2 jours). Rendre le socle sûr et crédible avant d'ajouter des fonctions.
  • Authentifier /ws (token + Origin + handshake hello), refuser un second client ou remplacer proprement l'ancien.
  • Corriger le deadlock de fermeture WS et ajouter un timeout/limite de connexions (fin des CLOSE-WAIT).
  • Centraliser is_forbidden_host sur toutes les routes, y compris /v2/cmd, avec parsing d'URL robuste et résolution DNS.
  • Corriger tabs_create (naviguer l'onglet réutilisé) et la fuite onAlarm.
  • Corriger les 5 bugs MCP (ping réel, read outline, wait, events limit, mime screenshot).
  • Brancher humanize-math.js sur les gestes CDP natifs.
  • Rotation des logs, GET /v2/info (versions démon + extension + capabilities).
Phase 1 — Socle fiable (1 semaine). Un canal identifié, reprenable et observable.
  • Session unique avec session_id, heartbeat ping/pong applicatif, reconnexion automatique de l'extension après perte du sink.
  • Idempotence : action_id + cache de résultat côté extension ; le démon peut réessayer sans double clic.
  • Annulation réelle : cancel par cmd_id, le geste s'arrête à l'expiration.
  • File par onglet côté démon et verrou global chrome.debugger.
  • Tests de déconnexion en cours de requête, de double exécution et de saturation.
Phase 2 — Moteur d'actions (1 à 2 semaines). Le vrai gain M2M.
  • Commande act batch : une liste d'étapes (goto, wait_for, click, type, scroll, extract) exécutée côté extension avec un seul timeout et un journal.
  • Modèle de cible unifié : {tab_id, frame_id, selector | text | role/name | rect}, résolution multi-frame (allFrames) et shadow DOM.
  • Vérification d'effet stable : MutationObserver + réseau idle, retour {changed, evidence, before/after}.
  • Outils MCP : dsh_act, dsh_extract, dsh_tabs, dsh_info, dsh_ping réel.
  • Commandes manquantes : tabs_list, tabs_close, window_create, window_focus, gestion des onglets épinglés et des dialogues alert/confirm/prompt.
Phase 3 — Navigation humaine (1 semaine). Le mode « comme un humain ».
  • Profils human_profile (calme / normal / pressé) avec seed reproductible pour les tests.
  • Trajectoires Bézier avec overshoot, bruit, pauses, vitesse variable ; frappe avec typos, backspaces, dwell lognormal, pauses de réflexion.
  • Mouvements périphériques entre actions, pauses de lecture proportionnelles au texte, scroll par blocs, focus/blur.
  • Apprentissage par démonstration : enregistrer les gestes d'Eddie et les rejouer avec variation.
  • Mode co-pilote : overlay de proposition d'action, validation humaine avant exécution sur les opérations sensibles.
Phase 4 — Observabilité et sûreté (1 semaine).
  • Métriques : latence, taux d'échec, commandes par onglet, reconnexions, sockets ouvertes.
  • Journal d'audit avec action_id, params redacted (jamais les valeurs de fill), durée et verified.
  • Rate limit par commande/onglet, allowlist par domaine et par commande, confirmation humaine pour eval et record/start.
  • Rotation et compression des JSONL, tableau de bord HTML temps réel.
Phase 5 — Déploiement et tests (1 semaine).
  • Source de vérité unique : un script deploy-extension.sh copie la version taguée vers dsh-eyes-extension-current ; plus de noms de dossiers trompeurs.
  • Handshake de version obligatoire ; GET /v2/info expose les versions et capacités.
  • CI GitHub Actions : cargo test, cargo clippy -D warnings, tests Node, build musl, zip et release.
  • E2E Chrome headless avec extension chargée : goto/read/click/fill/screenshot, reconnexion, double exécution, SSRF.
  • Tags v1.0.2, v1.1.0 et synchronisation Forgejo.

7. Innovations différenciantes

  • Co-pilote humain : l'agent propose une action surlignée dans la page ; l'humain valide ou corrige. Le meilleur des deux modes pour les consoles sensibles (GA4, GSC, Bing).
  • Learning from demonstration : enregistrer les gestes réels d'Eddie (souris, clavier, scroll) et les rejouer avec variation contrôlée. Le profil humain n'est plus inventé, il est appris.
  • Trust score par action : le démon note chaque action (sélecteur stable, effet vérifié, absence de captcha, domaine autorisé) et escalade vers l'humain sous un seuil.
  • Session recorder synchronisé : vidéo MP4 + trace JSONL des actions, alignées sur la même timeline — preuve exploitable pour un audit.
  • Multi-persona : profils « lecture », « achat », « admin » avec des paramètres de mouvement, de pause et de scroll différents.

  • tabs_create example.com → 200 en 0,87 s ; read mode:outline → 200 en 8 ms.

9. Phase 0 — implémentation (21/10/2026)

Le socle a été implémenté dans la branche main (commits 6ec8cb1, c4cf1ae, 20c49bd), version 1.1.0 :

  • Auth WS : token en query string, comparaison en temps constant, handshake hello (client, version, capacités) exposé par GET /v2/info ; page d'options pour saisir le token.
  • Deadlock : drop(handle) avant l'attente du bridge, timeouts de 2 s, zéro CLOSE-WAIT après redémarrage.
  • SSRF : validateur centralisé sur /v2/open, /v2/goto et /v2/cmd ; refus des IP loopback/privées/link-local/ULA et des formes déguisées ; backslash d'autorité refusé (bloquant trouvé par le contradicteur).
  • Rédaction : value, text, code, jetons et images masqués dans actions.jsonl.
  • Extension : tabs_create navigue l'onglet réutilisé, listener onAlarm idempotent, humanisation Bézier/typos/scroll branchée sur CDP.
  • MCP : dsh_ping réel, dsh_read avec mode, dsh_wait corrigé, dsh_events limité, mime screenshot correct, clic natif exposé.
  • Logs : rotation au démarrage au-delà de 50 Mo (3 archives).
  • Métriques (phase 4, première brique) : GET /v2/metrics expose volumes, issues, latence globale et par commande.
  • Tests : 135 passés, 2 ignorés ; nouveaux tests SSRF /v2/cmd, backslash, WS 401, rédaction, sérialisation par onglet, métriques.

Validation live (21/10, 22:34) : /health renvoie 1.1.0 ; /v2/info confirme l'extension connectée avec hello.version = 1.1.0 et ses capacités ; une seule socket ESTAB, zéro CLOSE-WAIT ; events.jsonl (55 Mo) rotaté en events.jsonl.1. E2E : tabs_create, read outline, screenshot (75 Ko), fill, type_native (valeur « hello »), click_native_text (verified:true après navigation), SSRF localhost 403 et backslash 400. actions.jsonl : 0 occurrence du secret de test, 5 entrées [redacted].

Limites restantes (phase 1) : redirections HTTP et DNS rebinding non re-vérifiés, eval reste une exécution JS arbitraire, token vide désactive l'auth WS sans alerte, MCP non câblé dans un client, tests record/hands toujours absents, stabilité 24 h à mesurer.

10. Verdict

Statut réel : phase 0 implémentée, testée (135 tests, clippy vert, binaire musl 1.1.0) et validée live ; première brique phase 4 (métriques) livrée. Portée réelle : Chrome personnel d'Eddie, extension 1.1.0 chargée et connectée, démon 1.1.0 actif, zéro CLOSE-WAIT. Prochaine étape : phase 1 (idempotence/annulation, reconnexion, cibles multi-frame), puis phase 2 (act batch) et E2E de non-régression.
